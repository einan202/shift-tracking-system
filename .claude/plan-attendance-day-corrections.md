# Plan (v5): Employee-owned attendance in three milestones

Branch: `feature/attendance-day-corrections` (from `main` at `68d68a0`). Save as `.claude/plan-attendance-day-corrections.md` (Step 0). No implementation, commit, push or PR until approved. Supersedes earlier versions.

## Context
Phase 1 shipped punches (API time, immutable) plus admin-made Add/Adjust corrections. The new model: **the employee runs the daily workflow** (clock in/out, fix a missed or wrong clock-in/clock-out with a reason, add a missing shift, delete a shift with an alert); **the admin reviews history and approves the month**. Work is split into **three milestones**, each completed and verified before the next starts; after each one we decide together whether to continue, based on progress and time.

## How we work (applies to every iteration)
- **The app stays functional after every iteration** (old screens keep working until replaced; each commit builds, tests green, `verify-all.sh` passes).
- **End-to-end flow first:** each iteration delivers a thin working slice (API + minimal UI + tests) before extras.
- Small increments, one logical change per commit; before each commit I list the proposed commits (message + explicit file paths) and wait for your confirmation; stage explicit paths only; no push and no PR until you say so; never merge.
- Backend changes ship with tests; the automatic verification (`/verify` / `verify-all.sh`) runs after each backend or frontend change; each milestone ends with the full suites, a Chrome pass, an independent `/review`, a short report and **a stop for your go/no-go**.
- Migrations never delete or rewrite existing data (legacy corrections preserved). A milestone adds only the schema it needs.

## Deadline priority (small, demonstrable steps)
The iterations are ordered so that something visible and working exists after each one: **1.0** navigation (frontend only, demo immediately) -> **1.1** safe schema foundation (no visible change) -> **1.2** schedules and employee configuration -> **1.3** the new timesheet table -> **1.4/1.4b** employees fix their own times -> **1.5** delete with alert -> **1.6** live Clock Out timer -> **1.7** admin history and retired admin corrections -> **1.8** Milestone 1 verification. If time runs short, stop after any iteration with a working app; the independent items (1.0, 1.6) can be shown on their own. Milestone 2 starts only after your go/no-go.

## Core requirements (approved, preserved in all milestones)
1. **Admin-made corrections are retired**; **all existing admin corrections stay with their effective results** (legacy parity).
2. **Table shows every calendar day**; columns **Date | Day | Clock-in | Clock-out | Worked | Expected | Balance**; Balance `+3h` (green), `-1h 6m` (red), `0` (grey). **Future days show Expected only (muted, no actions); Worked and Balance empty.**
3. **One consolidated effective shift per day** (first clock-in, last clock-out, manual corrections applied; breaks count as worked). Employees see only that; **no punch history or audit logs for employees**; only admins expand a day to see every interval.
4. **Manual times are orange, field by field**, with a non-colour "Manual" tag; admins see reason, time set and who.
5. **Employee operations (all with a reason, standard set or Other + text):** fix a missing or wrong clock-in/clock-out, add a missing shift, **delete a shift with an alert** (not while open). Previews show the **effective before/after result**, never raw audit history. Punches are never altered.
6. **Reasons:** Forgot to clock in; Forgot to clock out; Wrong time punched; Duplicate or accidental punch; Worked offsite or other location; System or time-service problem; Other (text required).
7. **Pay/shift config (admin):** pay type Monthly (Hourly stored, disabled); **working weekdays selected individually, each with its own expected duration (h/m)**; no fixed start/end times. **Schedules are effective-dated:** the weekday durations (and the overnight setting) live in **schedule versions with an effective date**; every date is calculated with the version applicable to that date, so **a schedule change never retroactively affects past months** (it can only take effect from the first day of the current Zurich month or later), and **submitted/approved snapshots stay immutable**.
8. **Live Worked timer only on the Clock Out button** (display only, server-computed seconds, never determines the clock-out, which always comes from the external time API); **reports never count unfinished work**; today's row shows Expected and the clock-in, Worked/Balance empty until clock-out; month summary has **month to date** (through today, today joins once finished) and **whole month** (Expected).
9. **Monthly closing rules (Milestone 2):** a month can be submitted **only after the calendar month has ended, starting on the 1st of the following month (Zurich date)**; validation **only at submission**; daily clock in/out and corrections are never blocked by it; expected working days need a complete valid pair, a manual fix, or an **absence reason (Sick Leave, Vacation, Other)** that counts as no worked hours and keeps the negative Balance; no explanation for non-working days without attendance; months submitted **in chronological order starting from the employee's employment start month** (an earlier Open or rejected month blocks only the next submission and the screen names the month to submit first; Pending Approval or Approved is enough); **no interval may still be open in the month at submission** (an open interval must be closed first, so an absence declaration can never leave a punch that could later change a submitted or approved month); after submission the month is **locked by the backend** and read-only in the UI until admin rejection or reopening; holidays are **manual, organization-wide and simple**: Expected = 0, attendance unaffected, **holiday updates are never blocked by anybody's locked month** and submitted/approved results are preserved by their **snapshots**; deadlines are **informational only**, never block, and nothing is ever approved or closed automatically.
10. **A real Clock Out on a later Zurich date never automatically counts as the effective end of the earlier day.** The original API punch is always preserved, but the earlier day's effective end time requires a **reasoned manual correction**; until then the interval is shown as "needs correction" and **is not counted as worked hours at all** (the multi-day span is never temporarily counted). The 24-hour limit is handled safely. **Exception by configuration:** an employee flagged **"overnight shifts allowed"** (admin setting, default off, for night workers) has a later-date clock-out within 24 h counted automatically on the shift's start date. See "Forgotten clock-out across days".
11. **Zurich time rules unchanged:** server clock only for audit timestamps, "not in the future" and display-only values; admin/employee times entered as Zurich wall-clock (+ offset only for the repeated DST hour); 24 h cap; no overlap across the effective set; per-user lock; busy -> 503.

## Forgotten clock-out across days (never auto-counted; 24-hour limit handled safely)
Scenario: the employee clocked in Monday 09:00, forgot to clock out, and notices on Thursday 08:00.
1. **Clock out with the real API time (unchanged punch rules).** The existing "clock-in while a record is open -> 409" rule stays, so the employee presses **Clock Out**; the punch stores the real API time (Thursday 08:00). **Punches are never capped, altered or deleted**, so this always works, even beyond 24 h; the original clock-out stays in the admin history.
2. **That clock-out does not count for Monday.** Because it falls on a later Zurich date than the clock-in date, Monday's interval becomes **"needs correction"**: its effective end is unresolved, Worked/Balance are empty, it is excluded from every total, and **the multi-day span is never counted, not even temporarily**. The record is closed, so the employee can **clock in again immediately**.
3. **Reasoned manual correction sets the effective end.** After such a clock-out the app offers "Set the real end time of Monday's shift" in the edit dialog (Monday's date, reason "Forgot to clock out" preselected, effective before/after preview). The correction row carries reason, time and actor; only then does Monday count (e.g. 8.5 h to 17:30). A reasoned correction is the explicit confirmation, so it may also set an end on a later date (a one-off overnight shift), within the 24 h cap.
4. **Exception by configuration:** for an employee whose applicable schedule version (for the shift's start date) has **"overnight shifts allowed"** (admin setting, default off; effective-dated so past shifts are never reinterpreted) a later-date clock-out **within 24 h** counts automatically and the shift belongs to its start date; longer than 24 h always needs correction.
5. **24-hour limit rules:** the cap applies to the **effective** interval (checked against the corrected clock-in/clock-out), never to the original punch. Correcting 71 h down to 8.5 h passes; a correction that still yields more than 24 h is rejected with a clear message (including the computed length) and nothing is written. A shift that genuinely lasts longer than 24 h is not supported (backlog).
6. **Overlap and ordering:** while an interval needs correction, overlap checks use its **raw punch span**, so shifts cannot be added inside it until it is corrected; the dialog explains the order (correct the stale shift first, then add other days). Corrections still satisfy not-in-the-future, no-overlap and Zurich/DST handling (ambiguous hour needs the offset); edits are atomic and previewed.
7. **Display and timer:** the day shows the clock-in with a "needs correction" tag (no Worked/Balance); the Clock Out timer for a still-open stale shift counts from that shift's own clock-in and is formatted beyond 24 h (for example `71:02:15`).
8. **Monthly submission:** an open interval in the month must be closed first (clock out, then correct) and cannot be covered by an absence; a "needs correction" interval must be corrected or the day covered by a declared absence (the raw punch stays, nothing counts). See the validation table and the locking rules.
9. Directly setting the clock-out of an open past shift without punching remains possible through the same edit, but the UI guides the clock-out-first path so the real API clock-out time is recorded.

## Calculations (shared by all milestones)
- **Shift of a day** = first effective clock-in to last effective clock-out; Worked = last out - first in (UTC difference, DST-safe); overnight shifts belong to the Zurich date of their first clock-in. A day with an open interval has no Worked/Balance (empty, "in progress").
- **Expected(date)** = the duration for that date's weekday in the **schedule version applicable to that date** (0 if the weekday is not selected, and 0 for dates before the employee's **employment start date**); in Milestone 2 also 0 on an organization holiday. Whole-month Expected = sum of all dates; month-to-date = dates up to and including today (Zurich date from the server), today counted once its shift is finished.
- **Later-date clock-out:** a closed punch whose clock-out Zurich date is later than its clock-in date counts only if the employee has **overnight shifts allowed** and the length is at most 24 h; otherwise (and always when longer than 24 h) its effective end is unresolved ("needs correction") and nothing of it counts until a reasoned correction sets the end; the raw punch is always preserved.
- Past expected day without a shift: Balance = -Expected; past non-working day without a shift: dashes; non-working day with a shift: Expected 0, Balance = +Worked. Declared absence (Milestone 2): Worked 0, Balance = -Expected.

## Legacy corrections
No existing correction row is deleted or modified; the admin correction endpoint/UI are removed in Milestone 1. The only effect on old rows is a new `ReasonCode` column backfilled `'Other'`. Old Add/Adjust rows keep applying (latest per record wins; manual Add rows are separate intervals), appear in admin history with admin/reason/time, and their cells show as manual (orange). **Parity test** seeds representative legacy rows (adjust of a closed punch, closing a forgotten clock-out, manual Add, midnight and DST cases) and proves identical effective results before/after.

## Architecture seams used by the milestones
- **Interval operations** (void / adjust / add) executed atomically by a pure **planner** (also the preview), under the per-user `UserLock` in one transaction; employee operations are day-level façades over them (set shift, delete shift). Rows share a `BatchId`.
- **Schedule resolution** (one pure function, used by every calculation, snapshot and the later-date clock-out interpretation): the applicable version for a date is the one with the greatest `EffectiveFrom` not later than the date (ties: newest created); dates earlier than every version use the earliest version; dates before the employment start date have Expected 0. Historical months therefore always recompute with their own schedule.
- **Effective-model state "needs correction"** (derived, never stored): a closed punch with a later-date clock-out (unless overnight allowed) or longer than 24 h and no end-setting correction; excluded from Worked/Balance/totals, shown with a tag, raw span used for overlap.
- **`IMonthStateReader`** seam: in Milestone 1 it always answers Open (so edits are allowed); Milestone 2 implements it from `MonthSubmissionEvents`, adding locking without touching the edit code paths.
- Reused: `AttendanceRecords`, `AttendanceCorrections`, `EffectiveAttendance`, `CorrectionService` rules, `ZurichTime`, `AppUserProvisioner`, `format.ts`, `zurichDefaults.ts`, the no-browser-clock guard test.

## Risks and trade-offs
- **Manual times must never pass as punches:** separate, reasoned rows; originals and API times never changed; orange in both lists; admin sees reason, time and who plus the full day history; locking and approval gate with an immutable snapshot (Milestone 2).
- **Semantics change:** Worked = first in to last out (was sum of intervals), so totals change for existing data (derived, no data migration); weekday durations replace the company default in calculations (default only prefills).
- **Milestone 1/2 screens are plain and sit in today's layout;** Milestone 3 reorganizes them (accepted rework in exchange for a working flow early).
- Months never submitted stay Open indefinitely (never auto-approved/closed); manual holidays need admin upkeep.
- Month-to-date totals lag by today's shift until it is finished (by design).
- Locking is enforced in the application layer under the per-user lock (the least-privilege SQL user can still INSERT punches); no database trigger planned. Holiday/config changes are deliberately not blocked; snapshots are the protection for submitted/approved months.
- Bigger test rewrite because admin corrections are retired.

## Assumptions to confirm (change any you disagree with)
0. **Schedule changes:** the effective date of a new schedule version must be on or after the first day of the current Zurich month (suggested default: the 1st of next month); the initial version takes effect from the employment start date; past months are never recalculated; correcting a mistaken historical schedule is out of scope (would need a separate approval flow, backlog).
1. Chronological order: "earlier months" start at the employee's **employment start month** (the admin-entered start date, not the first attendance record); every month from there to the previous one must be Pending Approval or Approved; an empty month still needs its one-click submission. Existing employees get their start date backfilled from their earliest attendance (or the migration date if none), which the admin can correct. A month is submittable from the 1st of the following month (Zurich date).
2. Informational suggested dates are plain text in the banner (3rd for submission, 5th for approval); no colour states, no derived "overdue" flags.
3. Non-working day or holiday with no shift: dashes, no colour; future days show Expected only.
4. Holiday changes and employment-start-date edits are never blocked by locked months: Open months reflect them immediately, Pending/Approved months keep their snapshot until reopened and resubmitted. Schedule changes are effective-dated and prospective (see item 0), so they never alter past months at all.
5. The live timer shows time since the day's first clock-in (`hh:mm:ss`) on the Clock Out button only.
6. Existing rule stays: an open past record blocks the next clock-in until it is closed; the employee closes it with the real-API-time Clock Out and then corrects the effective end time (see "Forgotten clock-out across days").
7. New `DECISIONS.md` entries to propose after you approve wording (not written by me): employee-owned manual fixes (reasoned, orange, full admin history), first-in/last-out worked time, retiring admin corrections with preserved results, per-weekday individually selected durations, manual organization holidays, submit/validation/order/locking rules, display-only timer, the three-milestone approach.
