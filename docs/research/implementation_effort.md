# Implementation effort for time and attendance features (custom full-stack web app, small JS/TS team)

Note on method: web sources cover platform constraints, pricing, regulation and patterns. Effort sizes (S/M/L/XL, engineer-days) are NOT published benchmarks; they are my estimates and are listed under Inferences. Assumed baseline: 1-3 engineers, TypeScript, Postgres, a managed auth provider. Estimates are for a production-quality MVP of each feature, including tests, not a polished enterprise version. Sizing key: S = 2-5 days, M = 1-3 weeks, L = 3-6 weeks, XL = 6+ weeks.

## Q1. Which features are deceptively hard, and what are their main complexities and pitfalls?

### Takeaway
The deceptively hard items are time zones/DST (a cross-cutting data-model concern), offline sync, the pay-rules engine (rounding/overtime, with legal exposure), leave accruals, and shift scheduling with recurrence. Browser-side location and offline are constrained by platform limits (no iOS Background Sync, location is untrusted) rather than by code volume.

### Cited Findings
- Geolocation: the W3C spec says the API is agnostic to location sources and gives no guarantee it returns the device's true location; on desktops without sensors results fall back to IP-based location, which a VPN/proxy changes. So browser geofencing is advisory, not tamper-proof. — [W3C Geolocation REC](https://www.w3.org/TR/2025/REC-geolocation-20250818/); [BrowserLeaks Geolocation](https://browserleaks.com/geo)
- A W3C TAG design review proposes an "approximate geolocation" permission subordinate to "geolocation", showing that browsers may increasingly return coarser location, which would break tight geofences. This is a proposal, not shipped behaviour. — [W3C TAG #1131](https://tag-github-bot.w3.org/gh/w3ctag/design-reviews/1131)
- Offline sync: Safari on iOS does not support the Background Sync API (caniuse lists unsupported through 26.5); queued work only goes out when the app is reopened. Chrome has had it since v89. Background Fetch and Periodic Background Sync are also unsupported on iOS. — [caniuse](https://caniuse.com/wf-background-sync); [Apple forums](https://developer.apple.com/forums/thread/694805); [Chrome blog](https://developer.chrome.com/blog/background-sync/?authuser=0); [firt.dev](https://firt.dev/notes/pwa-ios/)
- Web Push works on iOS/iPadOS from 16.4 but only for apps installed to the home screen (needs manifest + service worker); not for plain browser tabs. One blog claims push does not work for EU PWAs after iOS 17.4 (unverified blog claim). — [Braze](https://www.braze.com/resources/articles/mobile-web-push-is-now-supported-on-safari); [MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide); [slightfuture](https://slightfuture.com/webdev/progressive-web-apps-2026/)
- Offline conflict policies seen in timekeeping products: newest-edit-wins per entry (timesheet.io), online entry wins with offline entry flagged until someone deletes one (Jibble), offline events treated as the conflicting side (VeriClock), per-day user choice commit/discard/combine (Deltek). Idempotent sync is advised so retries do not create duplicates. Last-write-wins is simple but silently discards edits. Mostly vendor help pages, not independent evaluations. — [timesheet.io](https://timesheet.io/en/blog/offline-time-tracking-sync); [Jibble](https://www.jibble.io/help/how-to-track-time-without-an-internet-connection); [VeriClock](https://vericlock.zendesk.com/hc/en-us/articles/360048722511-Resolving-Offline-Event-Conflicts); [Deltek](https://help.deltek.com/product/Costpoint/Mobile/TimeandExpenseUserGuideAndroid/Sync_Records_Screen.html); [Hubstaff](https://hubstaff.com/time-tracking/accurate-offline-time-tracking); [DEV: field ops audit trails](https://dev.to/alichherawalla/mobile-data-sync-for-enterprise-field-operations-audit-trails-without-cloud-dependency-2026-32j8)
- DST: a shift spanning the fall-back change can show a clock-out earlier than clock-in in naive local time. — [Data-Basics](https://blog.data-basics.com/daylight-saving-time-creates-a-mini-y2k-crisis-twice-a-year)
- Temporal API: ships in Chrome 144+ and Firefox (139 first to support, per source), TC39 Stage 4 July 2026 per one source; Safari stable still lacks it per caniuse (a DEV post claiming Safari 18+ support conflicts with caniuse and is unreliable). Use a polyfill (or date-fns-tz/Luxon) for now. — [caniuse Temporal](https://caniuse.com/temporal); [InfoQ](https://www.infoq.com/news/2026/02/chrome-temporal-date-api); [web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/temporal)
- Recurring schedules: keep the IANA TZID with DTSTART; iCalendar requires VTIMEZONE when a rule crosses a DST shift; local times falling in a DST gap are ambiguous/invalid; several rrule libraries have had bugs resolving recurrences in UTC or losing zone info, causing shifted or duplicated instances. Test expansion across DST transitions in the chosen library. — [rust icalendar tests/docs](https://docs.rs/crate/icalendar/latest/source/src/recurrence.rs); [jakubroztocil/rrule issue 300](https://www.github.com/jakubroztocil/rrule/issues/300); [Drupal iCal issue](https://www.drupal.org/project/ical/issues/1071036)
- Rounding rules: FLSA 29 CFR 785.48 allows rounding to nearest 5 min, 1/10 hour or quarter hour, but only if it averages out neutrally over time; courts look at applied neutrality as well as facial neutrality (Corbin v. Time Warner, 9th Cir. 2016 upheld; a 2026 DOL opinion letter found a hospital rounding early clock-ins but barring early clock-outs not neutral). Commentators recommend keeping raw punches. Rules vary by jurisdiction and I did not research non-US law. — [Cornell LII 785.48](https://www.law.cornell.edu/cfr/text/29/785.48); [Ogletree on Corbin](https://ogletree.com/insights/ninth-circuit-approves-neutral-time-clock-rounding-practice); [DOL FLSA2026-8](https://www.dol.gov/sites/dolgov/files/WHD/opinion-letters/FLSA/FLSA2026-8.pdf)
- Overlap prevention: Postgres exclusion constraints with btree_gist (employee_id WITH =, tstzrange WITH &&) prevent overlapping shifts/punch intervals at the DB level; ranges default to half-open [), so back-to-back shifts do not conflict; partial constraints can ignore cancelled rows; PG18 adds WITHOUT OVERLAPS (per one source, verify). — [Supabase range columns](https://supabase.com/blog/range-columns.md); [Better Stack temporal constraints](https://betterstack.com/community/guides/databases/postgres-temporal-constraints/); [Django docs on Postgres constraints](https://docs.djangoproject.com/en/5.2/ref/contrib/postgres/constraints)
- Face liveness: AWS Rekognition Face Liveness is priced per check; a third-party site reports $0.015/check for the first 500k/month (not verified on AWS pricing page); a re:Post answer says failed attempts are billed too. — [AWS Face Liveness](https://aws.amazon.com/rekognition/face-liveness); [Stork.ai](https://stork.ai/en/amazon-rekognition); [re:Post](https://repost.aws/questions/QUvjRd9nCgS66oQ_Vv1rLJUg/how-does-amazon-rekognition-liveness-charges-users-per-successful-or-unsuccessful-attempt-or-both)
- SSO: WorkOS reported at $125/connection/month for SSO and separately for Directory Sync (SCIM), tiered down at volume (third-party figures, check workos.com/pricing). — [Clerk comparison](https://clerk.com/articles/the-real-cost-of-enterprise-sso-per-connection-vs-per-mau-p-3.md); [SSOJet](https://ssojet.com/blog/workos-pricing-at-scale-50-100-200-connections)
- Build vs buy context (low quality, vendor-oriented): one source estimates ~4.5 months and ~$36,000 to build a custom timekeeping solution; a Kronos reseller quote showed low per-employee pricing. Treat as anecdotal. — [TimeTrex cost-benefit](https://www.timetrex.com/blog/analysis-of-time-and-attendance-software); [business.com Kronos](https://www.business.com/reviews/kronos/)

### Inferences
Effort table (my estimates; ranges assume a managed auth provider, Postgres, and a team that has done web apps but not payroll domains). "Hardness" = ratio of hidden to visible effort.

| Feature | Size | Eng. effort | Deceptive? | Main complexity / recommended approach / pitfall |
|---|---|---|---|---|
| Basic clock in/out, server timestamps | S-M | 4-10 days | Low | Server sets time (never trust client); store client time only as a claim. Enforce one open punch per employee with a partial unique index; idempotency key for retries. Pitfall: forgotten clock-outs, double taps, accepting client-supplied timestamps. Real time-sync/tamper resistance beyond "server time" (NTP-checked kiosks, device attestation) is out of reach for a browser. |
| Timesheets, manual edit + approval | L | 3-5 weeks | Medium-High | Derive timesheet from punch events plus adjustments; never mutate punches. Approval state machine (draft/submitted/approved/locked/reopened), pay-period locking, edits after payroll export. Pitfall: edit-after-approval and period-close semantics. |
| Auth + RBAC + multi-tenant/multi-location | M-L | 2-4 weeks | Medium | Use managed auth (Clerk/Auth0/WorkOS/Supabase Auth/Better Auth). Roles are hierarchical and scoped (manager of which locations/teams), which is harder than a role column. Postgres RLS as safety net (see Q3). |
| Geolocation/geofencing | M | 1-2 weeks | Medium | Capture lat/lng/accuracy; compare with accuracy radius; store as evidence plus flag, not hard block, unless policy requires. PostGIS ST_DWithin or simple haversine is enough for circles. Pitfalls: permission denied, indoor accuracy of tens to hundreds of metres, IP-fallback on desktop, spoofing via devtools/VPN/emulation; iOS permission re-prompts. Can't be made tamper-proof in a browser. |
| Photo/selfie capture | S-M | 3-8 days | Low | getUserMedia/file input capture, upload to object storage with signed URLs, compress. Pitfalls: privacy law/retention/consent, storage cost, permission UX on iOS, stolen-photo spoofing (a photo alone is weak evidence). |
| QR/PIN kiosk mode | M | 1-2 weeks | Low-Medium | Kiosk device registration + long-lived device token, PIN hashed with rate limiting, lockout; rotating signed QR (short TTL) if QR is displayed by the kiosk. Pitfall: shared-PIN buddy punching, PIN brute force (4-digit space), kiosk session hijack, scoping device to one location. |
| PWA offline + sync | XL | 4-8 weeks to do properly | HIGH | Treat punches as append-only events with client-generated UUIDs; server idempotent upsert; show "pending" state; flush on app open/online (iOS has no Background Sync). Workbox for caching/queueing, IndexedDB (Dexie/idb) for store. Conflict policy must be product-decided (flag-and-review is the most auditable). Pitfall: device clock skew on offline punches (record both device time and monotonic offset, server received_at, and flag large skew), stale service workers, iOS storage eviction, rules that need server data (open punch state) while offline. Could drop scope to "offline queue only" (L, 2-3 weeks). |
| Break tracking | S-M | 4-10 days | Medium | Model breaks as sub-intervals or as punch types; paid vs unpaid; auto-deduct rules; compliance (meal-break violations, jurisdiction-specific). Deceptive because it feeds the rules engine. |
| Overtime/rounding/pay rules engine | XL | 6-12+ weeks for configurable; 2-3 weeks for hard-coded single policy | HIGH | Separate raw punches from computed "pay segments"; make computation deterministic, versioned, re-runnable (recalc when rules or edits change). Weekly/daily OT, double-time, holiday/premium, per-location/union rules, workweek boundaries across timezones, split shifts, rounding neutrality (legal risk per FLSA findings). Recommend start with a code-defined policy per tenant (strategy objects + test fixtures table) rather than a UI rule builder. Pitfall: configurable-engine scope creep; recalculation after retroactive edits; unrounded raw data must be kept. |
| Audit trail | M | 1-2 weeks if designed at the start; L if retrofitted | Medium | Append-only events table plus audit_log (who, when, what, before/after, reason, IP); DB-level revoke UPDATE/DELETE, optionally hash chaining for tamper evidence. Pitfall: logging only application-level actions and missing direct edits; PII in logs. |
| Shift scheduling + swaps | L-XL | 4-8 weeks | HIGH | Recurring templates (rrule + IANA zone), publish/draft states, conflict/overlap detection (Postgres exclusion constraints), availability, swap/offer/approval flows, labour-law constraints (rest periods), schedule-vs-actual comparison. Pitfall: DST on recurring wall-clock shifts; swap state machines and race conditions; drag-and-drop calendar UI cost (use FullCalendar/Schedule-X or similar but expect customisation). |
| Leave/PTO accruals | L-XL | 4-8 weeks | HIGH | Ledger model (append-only accrual/usage/adjustment transactions; balance = sum) instead of a mutable balance column. Policies: accrual per hour worked or per period, caps, carryover, proration, tenure tiers, negative balances, half days, holiday calendars by location, retroactive changes. Pitfall: backdating and recalculation; country-specific rules. |
| Notifications (email/push/SMS) | M | 1-3 weeks | Low-Medium | Email via Resend/Postmark/SES (S); Web Push via web-push lib or OneSignal/Novu/Knock (M; iOS only for installed PWAs); SMS via Twilio (carrier registration/10DLC lead time in the US is the hidden delay). Use a notification-preferences table + outbox/queue. |
| Reports + CSV export | M | 1-3 weeks | Medium | SQL views/queries over derived data; stream CSVs; time-zone-aware date grouping; formula injection (prefix =,+,-,@) in CSV; large exports via background job. Pitfall: reports must match payroll-rules output exactly; decimal vs HH:MM formats. |
| Payroll/accounting integrations + public API/webhooks | L-XL | 3-8 weeks (public API+webhooks M; each integration M-L) | Medium-High | Start with CSV export in the payroll vendor's import format; then unified-API providers (Merge, Finch, Rutter or similar, check pricing) or direct APIs (Gusto, QuickBooks, ADP). Public API: API keys/OAuth, versioning, rate limits, signed webhooks with retries/outbox. Pitfall: employee/earning-code mapping, per-vendor approval/partner programs, API certification timelines. |
| SSO (SAML/OIDC) | M if buying | 3-10 days with WorkOS/Clerk/Auth0; 3-6 weeks DIY | Medium | Per-connection cost (WorkOS reported $125/mo each for SSO and SCIM, third-party figure). SCIM provisioning adds more. Pitfall: per-tenant IdP config UX, JIT provisioning, role mapping, enterprise support burden. Defer until a customer asks. |
| Biometric/face verification | L-XL | 2-6 weeks (managed API) | HIGH (legal) | Managed options: AWS Rekognition (Face Liveness + CompareFaces), Azure Face (gated access), Face++/other; client SDKs for liveness. Pitfall: biometric privacy laws (e.g., Illinois BIPA, GDPR special category data; not researched in depth here), consent/retention, bias/false rejects, liveness cost per attempt (billed even on failures per re:Post), fallback flow. Recommend photo + review before biometrics. |
| Timezone/DST handling | M but cross-cutting | 1-2 weeks upfront, then ongoing | HIGH | Store instants as timestamptz (UTC); store each location's IANA zone; store workday/pay-period local dates computed at write time with the zone in effect; scheduled shifts stored as local time + zone. Pitfalls: 23/25-hour days, shifts crossing midnight and pay-week boundaries, ambiguous fall-back hour, zone rule changes (tzdata updates), employee traveling vs location zone, "which timezone does a report use". |
| Real-time dashboards | M | 1-2 weeks | Low | SSE/WebSocket or Postgres LISTEN/NOTIFY, Supabase Realtime/Ably/Pusher, or just polling every 15-30 s (S). "Who's in now" is a simple query on open punches. Pitfall: tenant scoping on channels; fan-out cost at scale. |

Rough totals (inference): lean MVP (clock in/out, timesheets with approval, RBAC, basic rules, CSV export, audit, notifications by email) about 10-16 engineer-weeks; adding scheduling, accruals, offline PWA, geofence/photo, kiosk brings roughly 30-45 engineer-weeks; payroll integrations, SSO, biometrics, a configurable rules engine push toward a year of small-team work. These totals are my judgement and not sourced; the only external reference found is one vendor-oriented anecdote of ~4.5 months / $36k for a simpler custom build.

## Q2. What libraries, services or managed options reduce effort?

### Takeaway
Managed auth/SSO, Postgres features (timestamptz, tstzrange exclusion constraints, PostGIS, RLS), Workbox/IDB libraries, Web Push or push services, and managed face-liveness APIs cut the most effort; nothing off-the-shelf solves the pay-rules engine or accruals, which are the best candidates for buying (white-label/embedded) or aggressively descoping.

### Cited Findings
- Temporal polyfill or Luxon/date-fns-tz needed for Safari until native support lands. — [caniuse Temporal](https://caniuse.com/temporal)
- Postgres btree_gist + tstzrange exclusion constraints for overlap prevention; PG18 WITHOUT OVERLAPS. — [Supabase](https://supabase.com/blog/range-columns.md); [Better Stack](https://betterstack.com/community/guides/databases/postgres-temporal-constraints/)
- Postgres RLS guidance (AWS Prescriptive Guidance, Crunchy Data and others): enable RLS on all tenant tables, FORCE ROW LEVEL SECURITY when the app connects as table owner, run the app as non-owner, use SET LOCAL per transaction (PgBouncer transaction mode can leak session settings), index tenant_id, keep app-level filtering too, views need security_invoker (PG15+), test cross-tenant isolation in CI. — [AWS Prescriptive Guidance RLS](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/rls.html); [Crunchy Data](https://crunchydata.com/blog/row-level-security-for-tenants-in-postgres); [ClickHouse multi-tenant guide](https://clickhouse.com/resources/engineering/multi-tenant-saas-postgres-architecture)
- Web Push on iOS requires installed PWA + manifest + service worker. — [Braze](https://www.braze.com/resources/articles/mobile-web-push-is-now-supported-on-safari)
- AWS Rekognition Face Liveness is a pay-per-check managed service (rates third-party, unverified). — [AWS](https://aws.amazon.com/rekognition/face-liveness)
- WorkOS SSO/SCIM per-connection pricing as above. — [SSOJet](https://ssojet.com/blog/workos-pricing-at-scale-50-100-200-connections)
- Clerk publishes comparisons of auth platforms that include SSO/SCIM in base tiers (vendor source, treat as marketing). — [Clerk](https://clerk.com/articles/auth-platforms-with-sso-and-scim-in-the-base-tier.md)

### Inferences
Suggested stack shortcuts (from my knowledge, not verified in this session; check current pricing/versions):
- Auth/RBAC: Clerk, Auth0, WorkOS, Supabase Auth or Better Auth for login/orgs; keep authorization (scoped roles) in your own code, e.g., with CASL, Cerbos or Oso.
- DB: Postgres (Neon/Supabase/RDS) + Drizzle/Prisma/Kysely; PostGIS only if polygons/many sites (circles do not need it).
- Offline: Workbox + Dexie/idb; consider sync engines (PowerSync, ElectricSQL, RxDB, Replicache/Zero) only if you need rich offline editing; for punch-only offline an append-only outbox is simpler and more auditable than CRDTs.
- Jobs/outbox: pg-boss, BullMQ, Inngest, Trigger.dev for rounding recalcs, exports, webhooks, notification fan-out.
- Notifications: Resend/Postmark/SES; web-push lib or Novu/Knock/OneSignal; Twilio.
- Calendar UI: FullCalendar or similar; rrule.js with caution (see DST bugs).
- Face: AWS Rekognition (Liveness + CompareFaces), or defer.
- Payroll connectors: unified HR/payroll APIs or CSV first.
- Build-vs-buy: consider embedding an open-source engine (Kimai for time tracking, TimeTrex, OrangeHRM, Frappe HR for leave/accruals) as reference for rules/accrual modelling, subject to licences (some are AGPL/copyleft; verify).

## Q3. What must be designed into the data model on day one (costly to retrofit)?

### Takeaway
Day-one items: immutable append-only punch events with server-received time, UTC instants plus IANA zone per location (and local work-date), tenant_id on every table (with RLS), an audit log, idempotency keys, ledger-style balances, versioned rules/policies, and period locking. Features like geofencing, photos, kiosks, SSO and notifications can be added later with modest rework if these foundations exist.

### Cited Findings
- Keep raw punch data separate from rounded/payroll totals; commentators advise retaining original clock records because a rounded total is not the original record, and rounding legality depends on how it is applied. — [Cornell LII 785.48](https://www.law.cornell.edu/cfr/text/29/785.48); [Ogletree](https://ogletree.com/insights/ninth-circuit-approves-neutral-time-clock-rounding-practice); [clockspot rounding](https://www.clockspot.com/research/time-clock-rounding-rules)
- Idempotent sync needed so retries do not duplicate entries; conflict policy should reflect data meaning. — [Hubstaff](https://hubstaff.com/time-tracking/accurate-offline-time-tracking); [DZone](https://dzone.com/articles/offline-first-sync-conflict-resolution)
- Postgres RLS needs tenant_id on every tenant table and indexes on it; SET LOCAL context per transaction. — [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/rls.html)
- Recurring-schedule storage should keep the IANA zone with the local start time. — [icalendar recurrence tests](https://docs.rs/crate/icalendar/latest/source/src/recurrence.rs)
- Postgres exclusion constraints can enforce non-overlap at the database level. — [Supabase](https://supabase.com/blog/range-columns.md)

### Inferences
Costly-to-retrofit checklist (ranked by retrofit pain, my judgement):
1. Tenant_id (and location_id) on every table from the start, composite FKs including tenant_id, RLS policies; retrofitting means backfills, key changes and security review across all queries.
2. Immutable punch/event log: events (clock_in, clock_out, break_start, break_end, edit, void) with id (client UUID for idempotency), employee, tenant, location, source (web/kiosk/offline/manual), `occurred_at_device`, `received_at_server`, `effective_at` (post-correction), device/kiosk id, geo+accuracy, photo ref, flags. Corrections are new events referencing the original, never UPDATE/DELETE. Timesheet is a derived view.
3. Time: timestamptz everywhere; per-location IANA zone stored; local work_date and pay_period computed and stored at write time with the zone used (so later zone changes do not rewrite history); recurring shifts as local time + zone.
4. Audit log table with append-only privileges (revoke UPDATE/DELETE), actor, reason, before/after; reason-required on manual edits.
5. Pay-period lock/versioning: approved/locked states and "recalculation run" records; versioned rules (effective-dated policies) so history is reproducible; store computed pay segments with the rule version that produced them.
6. Ledger model for leave balances (transactions with effective dates) plus effective-dated accrual policies.
7. Money/hours as integer minutes or fixed-precision decimals, never floats.
8. Soft-delete/status columns for employees (terminated staff retain history), employee <-> user separation (kiosk-only employees with no login), multi-membership (one person in several tenants/locations).
9. Idempotency keys and outbox table for webhooks/notifications/integrations; API versioning and stable external IDs.
10. Data retention/consent fields for photos/biometrics/location (privacy law dependent).
Cheaper to add later: reports, dashboards, notifications UI, SSO (if an auth provider with org support is chosen from the start), QR/PIN kiosk, geofence rules (if geo evidence is already stored on punches), photo capture (if a media ref exists).

- Legal retention requirements (e.g., FLSA record-keeping periods, GDPR) not researched in this pass.
